# 编码规则

## 权威范围

本文件是以下规则的唯一权威来源：

- 代码组织
- git 分支与 commit 方式
- 实验开关
- 日志埋点落位原则
- 文档同步要求

测试细则请看 [TEST_RULES.md](./TEST_RULES.md)，验收判定请看 [ACCEPTANCE_RULES.md](./ACCEPTANCE_RULES.md)。

## 总体编码原则

1. 优先保护原始 `mllm` 推理主路径，避免把实验逻辑直接塞进已有默认执行流。
2. 优先新增独立入口、独立模块、独立脚本；只有在复用价值明确时才接入现有实现。
3. 默认先建立可观测性，再做优化；没有 profiling 证据不进入“性能改造”。
4. 所有实验实现都要支持“默认关闭，显式开启”。
5. 每次改动只解决一个清晰问题，避免把基建、优化、重构混成一次提交。

## 术语与平台表述规则

- 在核心 restore 路径文档、代码注释、handoff、测试记录中，`host` 默认指 `target device host`，也就是 target device 上的 `arm64 CPU` 宿主侧。
- 若指 desktop / x86 Linux 开发机，必须显式写为 `x86 dev host`、`desktop host` 或 `host-side scaffold`。
- 不允许用 `host` 同时指代两种平台；若当前实现只在 `x86 dev host` 运行，必须主动写清“仅为 scaffold，不代表 target device 结果”。

## git 分支与 commit 规则

### 当前阶段分支基线

以下规则基于 `2026-03-13` 的仓库治理方案执行：

| 分支 | 角色 | 当前要求 |
| --- | --- | --- |
| `v2` | 稳定线 | 只接收已验证 PR，不承接日常开发 |
| `dev/v2-next` | 开发线 | 当前阶段默认开发基线 |
| `main` | 历史默认分支 | 短期冻结，不作为当前任务合入目标 |
| `v1` | 历史分支 | 短期冻结，不作为当前任务合入目标 |
| `hotfix/*` | 稳定修复线 | 仅当 `v2` 需要最小修复时，从 `v2` 切出 |
| `feat/*` | 特性支线 | 当 `dev/v2-next` 上任务过大时再拆分 |

### 分支规则

- 所有新开发默认在 `dev/v2-next` 或从其切出的 `feat/*` 上进行。
- `v2` 只作为当前阶段稳定主线，不直接承接日常开发。
- `main` / `v1` 短期冻结，不直接 merge 到 `v2`；若后续需要同步，必须单独评审。
- 若 `v2` 需要紧急修复，必须从 `v2` 切 `hotfix/*`，验证后通过 PR 回 `v2`。
- 一个任务建议对应一个分支或一个清晰主题。
- 特性分支命名建议：`feat/<task-id>-<short-name>`、`agent/<task-id>-<short-name>` 或 `exp/<task-id>-<short-name>`。
- 不在同一分支混入无关任务。

### push 与合流规则

- 不直接 push 到 `v2`。
- `v2` 禁止 force-push，默认只允许通过 PR 合入。
- 日常流程默认是：在 `dev/v2-next` 开发与推送，再通过 PR 合回 `v2`。
- 只有满足“测试证据 + 日志证据 + 实验逻辑默认关闭”的改动才允许申请合回 `v2`。
- 若当前 GitHub 侧尚未完成设置，应尽快将默认分支调整为 `v2`，并为 `v2` 开启最小保护。

### tag 规则

- 每个里程碑完成后，应在 `v2` 上打稳定 tag，作为可回退锚点。
- 当前方案的首个安全锚点建议为 `stable-v2-2026-03-13`。
- tag 只打在已验证的稳定提交上，不打在带未确认实验改动的开发提交上。

### commit 规则

- 必须小步提交，可回滚。
- 每个 commit 应能回答“改了什么、为什么改、如何验证”。
- 不允许把“实验框架搭建 + 性能优化 + 日志重命名”挤进同一个 commit。
- commit 信息建议包含 Task ID，例如：`T003: add flash device-host profiling hooks`.

## 目录组织规则

### 优先落位

| 类型 | 建议目录 |
| --- | --- |
| 独立实验入口 | `examples/` 或新增明确实验目录 |
| 可复用基准程序 | `benchmarks/` |
| 自动化或部署脚本 | `scripts/` |
| 回归或单元测试 | `tests/` |
| agent 协作文档 | `docs/agent/` |

### 组织要求

- 实验代码优先独立目录，命名体现用途，例如 `restore_benchmark`、`qnn_restore_probe`。
- 如果必须改动 `mllm/backends/qnn/` 或现有模型实现，改动应最小化，并用开关隔离。
- 不把一次性分析材料、临时日志、设备输出直接提交到源码目录。

## 实验开关规则

- 所有实验逻辑必须默认关闭。
- 开启方式必须显式，例如命令行参数、配置项、编译选项或环境变量。
- 开关命名应表达行为，不用含糊名称，如 `--enable-restore-benchmark`，不要用 `--debug2`。
- 开关开启后新增的行为、性能开销、日志变化必须在 handoff 中写明。

## 真机环境规则

- 涉及 QNN / Android 真机构建、部署、验证时，先按 [LOCAL_ENV.md](./LOCAL_ENV.md) 激活本机环境。
- 服务器路径、SDK 路径、conda 环境名优先维护在 `LOCAL_ENV.md`，不要分散复制到多个任务文档。
- 非本机通用的绝对路径不要硬编码进源码默认值；若脚本确需引用，必须在 handoff 中说明适用环境。

## 日志规则

### 基本要求

- 日志首先服务于 profiling、测试复现和问题定位，不做随意打印。
- 阶段命名必须稳定，避免同一阶段出现多个别名。
- 需要对比的数据必须带结构化字段，禁止只输出自然语言说明。

### 推荐字段

| 字段 | 说明 |
| --- | --- |
| `task_id` | 对应任务编号 |
| `run_id` | 单次运行唯一标识 |
| `scenario` | 场景名，如 warm/cold/restore |
| `model` | 模型或配置标识 |
| `backend` | CPU/QNN/AOT 等 |
| `device` | 设备或平台标识 |
| `stage` | profiling 阶段名 |
| `latency_ms` | 阶段耗时 |
| `tokens` | token 数 |
| `flag_set` | 本次显式开启的实验开关 |

## 文档同步规则

- 任务状态变化时同步更新 [TASK_BOARD.md](./TASK_BOARD.md)。
- 规则变化时只修改对应权威文件，不在其他文件复制一遍。
- 任何代码交付都应附带一份基于 [HANDOFF_TEMPLATE.md](./HANDOFF_TEMPLATE.md) 的结构化说明。
- 若新增目录或新实验入口改变协作方式，应先更新本文件或 `PROJECT_BRIEF` 再扩散执行。
